# Logitech G502 X LIGHTSPEED onboard editor

This experimental contribution adds onboard profile editing for the **Logitech G502 X LIGHTSPEED**. On this device, the existing pointer settings page exposed DPI but did not provide a complete onboard assignment workflow. The new **Onboard profiles** workspace groups assignments, sensitivity and onboard-memory management in one place.

This is an incremental implementation, not a claim of G HUB feature parity. The tested connection is the mouse attached directly by **USB cable**, even though the product name contains LIGHTSPEED.

## Hardware and compatibility

| Item | Observed or supported value |
| --- | --- |
| Tested mouse | Logitech G502 X LIGHTSPEED |
| Tested USB route | Vendor `046d`, product `c098` |
| Tested host | Windows x64 |
| Configuration feature | HID++ `0x8100` (onboard profiles) |
| Observed formats: memory / profile / macro | `1 / 3 / 1` |
| Observed user memory | 16 sectors, 255 bytes each |
| Observed profiles / button entries | 5 profiles, 11 entries per layer |
| Accepted layouts | Memory and macro format 1; profile format 3 or 5; 255- or 256-byte sectors |
| Receiver / other models | Not enabled by this contribution; no compatibility claim |

The office-mouse reprogrammable-controls feature `0x1b04` is not used as a substitute for `0x8100`. Acceptance of a layout in code is not evidence that every device or firmware advertising it has been tested. The eleven displayed button numbers are firmware indices, not verified G-number labels or physical hotspots.

## What is implemented

| Area | Behavior |
| --- | --- |
| Assignments | Ordinary and G-Shift layers; mouse buttons, keyboard shortcuts with modifiers, media controls and supported firmware actions |
| Sensitivity | Five DPI stages; default and DPI-shift stage selection; 100–25600 DPI in steps of 50; zero disables a non-selected stage |
| Report rate | 125, 250, 500 or 1000 Hz |
| Profiles | Read names and directory entries, rename a profile, activate or reload an enabled profile |
| Execution mode | Explicit host/onboard selection; reading and writing do not implicitly change mode |
| Drafts | Changes remain in the editor until written; discard restores the captured values; export validates without programming flash |
| Recovery | Full backups, exact write readback, last-write restore in the current editor session, and file-based CLI restore |
| Windows startup | GUI, agent and overlay use the GUI subsystem, without a console window; the diagnostic CLI remains a console tool |

Untouched bindings, existing macro references, erased name encodings and unknown profile bytes are preserved. Existing macro preservation does **not** mean macro authoring or execution has been implemented.

## Desktop workflow

1. Connect the G502 X LIGHTSPEED by USB cable. Close other device-settings programs before a write or mode/profile change.
2. Open the device and choose **Onboard profiles**, then **Read / refresh**. Reading does not write memory or change execution mode.
3. Use the profile selector to choose the profile to edit. Inspect its status in **Onboard memory**; inactive profiles can be edited without activating them.
4. In **Assignments**, select a firmware button index and its normal or G-Shift layer. Choose an action or enter a physical-key shortcut such as `Ctrl+Shift+A`, `PageUp`, `F24` or `Num1`, then assign it.
5. In **Sensitivity and report rate**, edit the five stages and select the default/shift stages. Those two stages must be nonzero.
6. Use **Discard changes** to abandon the draft, or **Write to mouse** to validate and save it. A full original capture and the requested patch are flushed to disk before flash programming begins.
7. After a successful write, use **Activate / reload profile** in **Onboard memory** when you want the mouse to load that profile. Saving an inactive profile does not switch the currently active profile.

The editor blocks profile switching and refresh while an ordinary unsaved draft exists. After an uncertain mutation failure, refresh is available to establish the actual device state; preserve the reported backup first.

### Restore the last write

**Restore profile N before last write** restores the original bytes from the most recent successful write retained by this editor. The label identifies the affected profile even while another profile is selected.

- Discard any unsaved draft before restoring.
- The device must be online, on the same route and in onboard mode.
- The agent captures and flushes the current memory before restoration.
- Restoration requires the complete memory to match the expected applied edit. Later changes to the target or another sector cause rejection instead of being overwritten.
- Success consumes the in-memory undo entry. Activate or reload the restored profile to use it.

This is one-level, session-local recovery, not a persistent undo history. Closing or recreating the editor loses the undo entry, but the on-disk pre-write edit file remains. Failed or partially programmed writes are not eligible for blind retry or automatic rollback.

### Backup files

Files live under `gaming-backups` in OpenLogi's active configuration directory. For the default Windows production profile, this is `%USERPROFILE%\.config\openlogi\gaming-backups`. XDG overrides and the development profile can change that location. The UI reports the actual saved path.

| File name prefix | Contents and purpose |
| --- | --- |
| `g502x-backup-` | Complete captured memory from **Back up onboard memory** |
| `g502x-prepared-` | Validated original capture plus draft patch; exporting does not apply it |
| `g502x-before-write-` | Original capture plus requested patch, flushed before a flash write; can be used for guarded CLI restore after a successful apply |
| `g502x-before-restore-` | Complete memory captured immediately before a restore attempt |

A raw backup is not the same schema as an edit file. Arbitrary backup import is not implemented. Keep backups and G HUB migration inventories private when reporting issues.

## Optional CLI recovery

Ordinary desktop use does not require CMD. The CLI is an optional diagnostic tool. Direct mutation commands reject a running OpenLogi agent and competing device managers; close those applications before using them.

For a previously applied edit file:

```powershell
.\bin\openlogi.exe gaming preview "g502x-before-write-EXAMPLE.json"
.\bin\openlogi.exe gaming restore "g502x-before-write-EXAMPLE.json"
```

Replace the example with the actual edit-file path. Preview is offline; restore accesses the mouse and enforces the same exact-state checks. It does not activate the restored profile. The CLI also exposes `inspect`, `backup`, `prepare`, `apply`, `mode` and `select`; use `gaming --help` for arguments.

## Architecture and write guarantees

The desktop is a pure IPC client. The agent owns the authoritative HID channel, excludes known competing settings processes, and retains its device lease until the complete transaction finishes, even if the IPC requester disconnects. The CLI and agent share the device-layer write/restore implementation. Process exclusion is best effort, not an operating-system lock against future device opens.

Before writing, the device layer validates the layout, directory/profile checksums, patch bounds and full-memory precondition. It rejects removal of the last ordinary left-click binding. Each modified sector is reread immediately before writing and verified byte-for-byte afterwards. Uncertain writes are never retried automatically.

While this model is in onboard mode, background host-DPI reconciliation yields to firmware. Explicit host-DPI requests explain that onboard settings must be edited instead. Other devices retain their existing host-DPI path.

The editor API uses append-only **IPC protocol 36**. Desktop, agent and overlay must come from the same build; replace them together rather than mixing old and new executables.

## Build and validation

The development preview was built on Windows x64 with Rust 1.99.0 and MSVC. The repository's toolchain, packaging and gate rules remain authoritative; see [Developing OpenLogi](../DEVELOPMENT.md).

```powershell
$env:VSLANG = "1033"
$env:RUSTFLAGS = "-D warnings"
cargo +1.99.0 build -p openlogi -p openlogi-agent -p openlogi-desktop -p openlogi-overlay
```

This produces a development build, not a signed upstream release. Keep the desktop, agent and overlay together; the optional CLI may be placed in `bin`.

### Evidence and remaining acceptance

On 2026-10-09, descriptor, directory and profile reads passed on the device described above. A name-only edit to an inactive enabled profile was written, read back and restored. A subsequent complete capture matched all sixteen original sectors byte-for-byte; execution mode and active profile were unchanged. This hardware round trip preceded the GUI restore addition.

The redesigned Windows workspace was inspected in a dark, approximately 1280 × 850 window. All three pages displayed; a report-rate change entered the unsaved state and discard restored the original draft. These UI checks did not program the mouse.

Synthetic tests cover CRCs, stale-state rejection, bounds, unknown-byte preservation, last-left-click protection, frame sequencing, failed transfers, keyboard encoding, wire-format goldens, locale wiring and editor draft state. Restore tests exercise successful readback, already-restored no-op, unrelated memory changes, target changes, host-mode rejection and a readback mismatch with no retry. Editor tests cover undo retention across refresh/export and its consumption after successful restoration.

The **new GUI restore button has not yet completed native interaction or real-device acceptance**. Also pending: every physical binding, host/onboard switching, other firmware revisions, wireless receiver routes, light/narrow/scaled UI states and native Linux/macOS builds. Synthetic tests and wasm checks do not substitute for these checks. The contribution stays a draft while those gaps are reviewed.

To repeat hardware acceptance, capture a fresh backup, identify an inactive enabled profile, change only its name, write/read back, restore, then compare a second complete capture. Record the model, USB IDs, descriptor, connection type, OS, exact commit and result; do not publish personal memory captures.

## Troubleshooting

| Symptom | What to check |
| --- | --- |
| Only the old pointer page appears | Confirm the running executable is the new build and all three peers were replaced; an existing singleton can keep the old process alive |
| Read or write reports unsupported device | Confirm direct USB cable connection and route `046d:c098`; receiver mode is outside this implementation |
| Write remains disabled | Read first, make a valid draft, confirm onboard mode, and resolve any required refresh |
| Device settings program is running | Exit its main program/background settings agent, then retry the intended operation |
| Memory changed since backup | Another writer or later edit changed memory; preserve the existing backup, refresh and create a new draft |
| Restore is unavailable | It needs a successful write retained in this editor session, a matching online route, onboard mode and no unsaved draft |
| Readback mismatch or uncertain transport failure | Preserve the backup and error, stop further writes, and inspect the device state; do not force or loop retries |
| Saved settings are not active | Explicitly activate/reload the edited profile after a successful write or restore |

## Limitations and provenance

Not implemented: multi-step macro recording/execution, per-game automatic switching, enabling disabled slots, wireless receiver support and arbitrary backup import. The optional `tools/ghub_profile_export.py` creates a read-only inventory of locally assigned G HUB settings; it does not log into G HUB or claim those macros have been imported.

Framing, memory layout and CRC behavior are based on the reverse-engineered [libratbag HID++ implementation](https://github.com/libratbag/libratbag/tree/8235b5bb6032dea15901ab58a8218956f4494d08/src), particularly `hidpp20.c`, `hidpp20.h` and `hidpp-generic.c`. This is not a published Logitech specification. No G HUB artwork, login tokens or personal captures are included in the contribution.
